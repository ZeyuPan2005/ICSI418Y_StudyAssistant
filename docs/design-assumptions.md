# Design assumptions and requirement decisions

The submitted Milestone 2 report is the baseline. Section 2 defines US-01–07, section 3 defines UC-01–05, and section 4 defines NFR-01–06. The UI implements the approved eight-screen scope for Milestone 3 Part 4.

| Decision | Basis and implementation |
|---|---|
| Targeted practice | Milestone 1 describes catered quizzes as a further goal. Milestone 2 makes follow-up practice MVP under US-04 and UC-04. The prototype follows Milestone 2. Each practice request from a graded lecture result creates a separate quiz and draft attempt with new IDs. The quiz references the source result. The source quiz, attempt, answers and grading snapshot stay intact. Practice draws distinct questions only on missed source topics. Additional practice sessions begin at the original lecture result. |
| Courses and enrollment | Milestone 2 leaves joining a course open. Preassigned memberships provide the study context. Maya is a student in both fictional courses. Eli has a submitted Software Engineering result. Jordan teaches only Software Engineering. The role switcher uses Maya or Jordan. |
| Supported files | MP3, WAV, PDF and PPTX are provisional formats. Validation checks selection, extension and nonzero size. The browser displays filename and size before confirmation. No MIME sniffing, binary decoding, file transmission or permanent file storage occurs. |
| Processing and generation | Milestone 1 mentions model training and API integration. Milestone 2 leaves the generation method open. The mock saves file metadata and points to the selected course’s fixture. Readiness follows a short timer. No audio transcription, slide parsing, AI concept extraction or model call occurs. Ten base questions per course support the lecture demo. A separate practice bank supplies two items per missed topic. |
| Failure fixtures | One seeded lecture has unusable content, another fails generation once per reset. A labeled quiz control simulates interrupted submission. These deterministic cases support repeatable demonstrations. Invalid files create no new lecture, so the unusable-content example is a separate seed. |
| Dates and reminders | The seven-day in-app window is provisional. Compare local calendar dates from today through today + 7 inclusive. Day +8 remains listed without a badge. Accept any valid four-digit calendar date (years 0001–9999), including past dates. Teachers can see and edit past items. Student lists show today and future dates. Recompute badges from current course records when displayed. This supersedes the original Phase A suggestion to reject past dates. Notification delivery outside the app is deferred. |
| Roles and privacy | Both actors can upload to accessible courses. Students generate and answer their own quizzes. Only an assigned teacher can publish, edit or remove course deadlines or inspect classmates’ submitted responses. The mock checks the actor, membership and ownership in its service functions. Role switching and local storage demonstrate the rules in a trusted browser. Production identity and enforcement belong on the server. |
| US-07 placement | Reviewing scores and answers is an MVP story outside the five critical use cases. Its dedicated view carries UI-01T within the teacher dashboard. Drafts are excluded from submitted results. The dashboard also hosts the lecture index and the student’s personal quiz/result index. |
| Persistence and reset | Demo state uses local storage per browser origin. The demo assumes one active writer, a current browser with storage enabled, and a loopback or secure origin for record IDs. Reset restores fixtures with dates relative to the reset day. The teacher and student see changes by switching profiles in the same origin. |
| Interface language | The app provides an English file-selection label and filename feedback. Deadline dates use an English YYYY-MM-DD text field with calendar validation. The native file dialog follows the operating system’s language. |
| Prototype controls and scope | Role switching, reset and deterministic failures support demonstrations. Exclude these controls from business processes and entities in the DFD and ERD. The approved product roles are Student and Teacher. Administration, enrollment, course creation, analytics and AI chat are outside this milestone. |
| Deferred validation | NFR-01 and NFR-02 need representative service/data-load timing. NFR-04 requires five first-time users. NFR-03 and NFR-06 need production enforcement and real connection recovery tests. Keyboard checks exercise NFR-05 prototype behavior. No production NFR certification is claimed. |
